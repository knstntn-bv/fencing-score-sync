# Фехтовальщики, история боёв и Supabase

План развития Fencing Scorer: справочник людей, выбор перед стартом таймера, сохранение результатов в удалённой БД. Текущий бой по-прежнему идёт на устройстве.

Сайт — статический SPA (GitHub Pages + опционально Capacitor). Бэкенд приложения не пишем: Postgres, Auth и RLS даёт Supabase.

## Зачем

Сейчас табло — чистый клиентский `useState`:

- имена зашиты как «Fencer 1 / Fencer 2»;
- настройки и матч исчезают при перезагрузке;
- победитель есть только по очкам, истечение времени никуда не пишется.

Нужно:

1. Хранить список фехтовальщиков в клубе.
2. Перед первым Start выбрать двух разных людей на синюю и красную сторону.
3. После завершения боя сохранить результат так, чтобы потом считать статистику **по человеку**, а не по цвету дорожки.

Синий/красный — роль в конкретном бою (как полосы на аппарате). Идентичность — `fencer_id` + снимок имени на момент боя. Один и тот же человек в разных боях может быть то синим, то красным; статистика всё равно склеивается по человеку.

## Принципы

- Источник правды для людей и протоколов — Supabase.
- Идущий бой (счёт, таймер, пауза) не уходит в сеть: табло не должно зависеть от Wi‑Fi на дорожке.
- `localStorage` — только кэш roster и очередь неотправленных результатов, не основная база.
- В запись боя всегда кладём **и id, и имена**. Id нужен для статистики; имя — чтобы протокол читался после переименования или архива.
- В клиент попадает только anon key. `service_role` в Vite/GitHub Pages не кладём.

## Что не входит в этот круг

- Realtime-табло на втором экране (это отдельный sync).
- Карточки, приоритет, периоды 3×3 по FIE.
- Несколько клубов и роли «тренер / судья» (закладываем `club_id` / `user_id`, не усложняем UI).
- Редактирование уже сохранённого боя.
- Нативный Capacitor-проект в git.

## Модель данных

### Фехтовальщик

```text
fencers
  id            uuid pk
  club_id       uuid not null          -- пока = auth.uid() или одна запись клуба
  name          text not null
  archived_at   timestamptz null       -- soft-delete: история не дырявится
  created_at    timestamptz
  updated_at    timestamptz
```

Уникальность имени в клубе: `(club_id, lower(trim(name)))` среди неархивных. Пустые имена запрещены.

Удаление из UI = архив. Строки в `matches` не каскадим.

### Бой

```text
matches
  id                 uuid pk
  club_id            uuid not null

  -- кто дрался (для статистики)
  blue_fencer_id     uuid not null references fencers(id)
  red_fencer_id      uuid not null references fencers(id)
  blue_name          text not null     -- снимок на момент боя
  red_name           text not null

  -- счёт и правила этого боя
  blue_score         int not null check (>= 0)
  red_score          int not null check (>= 0)
  time_limit_sec     int not null
  points_limit       int not null
  remaining_sec      int not null      -- сколько осталось на таймере в конце

  -- исход по человеку, не «победила синяя сторона» как единственное поле
  winner_fencer_id   uuid null references fencers(id)   -- null = ничья
  winner_name        text null
  ended_by           text not null check in ('points', 'time')

  started_at         timestamptz not null
  finished_at        timestamptz not null
  created_at         timestamptz
```

Ограничения:

- `blue_fencer_id <> red_fencer_id`;
- при ничьей `winner_fencer_id` и `winner_name` оба null;
- при победе `winner_fencer_id` совпадает с blue или red, `winner_name` = соответствующий снимок.

Цвет в этой таблице нужен, чтобы воспроизвести бой («Иванов был синим»). Для статистики запросы идут так:

```sql
-- все бои человека, независимо от цвета
select *
from matches
where blue_fencer_id = $id or red_fencer_id = $id
order by finished_at desc;

-- победы
select count(*) from matches where winner_fencer_id = $id;
```

Страница истории в v1 показывает имена (`blue_name` vs `red_name` и счёт), не «Blue won». Агрегаты (победы, уколы, винрейт) — отдельный шаг после того, как записи стабильно пишутся.

### Настройки

Лимиты времени и очков сейчас живут в `App.tsx` и теряются. В этом круге достаточно persist на устройство или одна строка `club_settings`. Не блокирует roster/историю.

### Клиентские типы

Держать в `src/types/` отдельно от UI. Стороны — `'blue' | 'red'`. Человек — `{ id, name }`. Результат боя всегда содержит оба.

Черновик идущего матча в память приложения, не в `matches`, пока бой не завершён.

## Что считать концом боя

Сейчас `winner` ставится только при достижении `pointsLimit`. Таймер в нуле вызывает `onStateChange(false)` так же, как Pause — этого мало.

Зафиксировать:

| Событие | Исход | `ended_by` |
|---|---|---|
| Счёт достиг лимита очков у одного | победа этого человека | `points` |
| Время вышло, счёт неравный | победа того, у кого больше уколов | `time` |
| Время вышло, счёт равный | ничья | `time` |
| Reset до конца | бой отменён, в БД не пишем | — |

Ручную кнопку «Завершить бой» на первом шаге не добавляем.

`Timer` должен отличать паузу от истечения и отдать родителю остаток секунд (`onExpire`, `timeLeft` / `onTick`). Иначе в протокол нельзя записать `remaining_sec` и `ended_by: 'time'`.

Сохранение — один раз на завершение, идемпотентно (флаг `savedMatchId` в состоянии матча). Повторный ререндер вторую строку не создаёт.

После успешной записи — «Новый бой»: сброс счёта и таймера, выбор сторон можно оставить или очистить.

## Auth и RLS

Первый контур: один клубный логин (email + пароль или magic link). Все `fencers` / `matches` с `club_id = auth.uid()` (или `club_id` из профиля, если сразу заведём `clubs`).

Политики: пользователь видит и меняет только свои строки. Anon без сессии таблицы не читает и не пишет.

Пока нет сессии: roster/история пустые, Start либо заблокирован, либо явно «гость, результат не сохранится». Скрытый гостевой режим без предупреждения не делаем.

Сессию на судейском планшете держать долго (remember).

## Офлайн

На дорожке сеть может пропасть в момент записи.

1. Живой бой — только RAM.
2. В конце — `insert` в Supabase.
3. Если ошибка сети — запись в очередь `localStorage` (`outbox:matches`), UI показывает «сохранится, когда появится сеть».
4. При старте приложения и по `online` — flush очереди.

Очередь маленькая и прикладная, не замена БД. После успешного insert элемент удаляется.

Кэш списка фехтовальщиков (последний успешный `select`) можно класть рядом, чтобы селекты открывались без сети. Стартовать бой с кэшированными id допустимо; результат всё равно уйдёт через outbox.

## UI и посадка на текущий код

Текущие точки:

- `App.tsx` — роутинг, settings state;
- `pages/Index.tsx` — счёт, `hasMatchStarted`, `winner`;
- `Timer.tsx` — время спрятано внутри;
- `ScoreDisplay` уже принимает `playerName`;
- `@tanstack/react-query` уже в зависимостях — им кормить roster и историю;
- shadcn `Command` / combobox есть.

Экраны:

1. **Логин** — простой экран или модалка до работы с данными.
2. **Список фехтовальщиков** (`/fencers`) — добавить / переименовать / архивировать. Не смешивать с лимитами в Settings.
3. **Табло** (`/`) — до Start два combobox (синий / красный). Можно создать имя оттуда же. Start неактивен, пока не выбраны двое разных. После `hasMatchStarted` селекты lock. Подпись победителя — имя, не «Fencer 1 won».
4. **История** (`/history`) — колонки: дата, имена, счёт, как закончился (`очки` / `время`), кто победил по имени. Фильтры по человеку — можно сразу простым select, полная статистика позже.
5. **Settings** — как сейчас, лимиты.

Навигация: к табло добавить ссылки на фехтовальщиков и историю (иконки рядом с шестерёнкой).

```text
roster → выбор синий/красный → Start → бой локально
   → лимит очков или время вышло → insert match (id + имена)
   → история / статистика по fencer_id
Reset до конца → обратно к выбору, без insert
```

## Инфра

- Проект Supabase, SQL-миграции в репо (`supabase/migrations/`), не клики в Dashboard как единственный источник схемы.
- Клиент: `@supabase/supabase-js`, обёртка `src/lib/supabase.ts`.
- Env: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`.
- GitHub Actions Pages: те же переменные как secrets, иначе прод-сборка будет пустой клиент.
- Локально `.env.local` (уже в `*.local` gitignore).

Capacitor не требует отдельного SDK: тот же JS-клиент.

## Порядок работ

Не смешивать схему, таймер и историю в одном заходе.

### Шаг 1 — фундамент

Supabase-проект, миграции `fencers` / `matches`, RLS, один пользователь. Клиент, логин, проверка что anon без сессии ничего не видит.

### Шаг 2 — справочник

CRUD имён, архив, уникальность. Страница `/fencers`. Кэш списка опционально.

### Шаг 3 — выбор на табло

Селекты, запрет одной персоны на обеих сторонах, lock после Start, имена на `ScoreDisplay`. `Start` без выбора не запускает таймер.

### Шаг 4 — честное завершение и запись

Таймер: expire ≠ pause. Правила исхода из таблицы выше. `insert` с id **и** снимками имён, `winner_fencer_id`. Outbox при офлайне. Идемпотентность.

Проверить вручную:

- бой до лимита очков → одна строка, имена совпадают с селектами, победитель — человек, не цвет;
- время вышло при 3:1 → победа лидера, `ended_by = time`;
- время вышло при 2:2 → ничья, `winner_fencer_id` null;
- Reset до конца → строк нет;
- тот же человек синий, затем красный → в истории две записи, статистика по id склеится;
- переименовать бойца после боя → старый протокол с старым `*_name`, новые бои с новым;
- офлайн в момент конца → очередь, после сети строка в БД.

### Шаг 5 — история

`/history` по `finished_at desc`, показ имён и счёта. Ссылка с главной.

### Шаг 6 — статистика по людям (после стабильной записи)

Отдельный экран или блок у фехтовальщика: бои, победы, поражения, ничьи, уколы за/против. Источник — `blue_fencer_id` / `red_fencer_id` / `winner_fencer_id`, имена только для подписи. Не делать этот экран, пока шаг 4 не пишет данные предсказуемо.

## Тесты

Важнее всего чистые функции, не e2e на Supabase:

- исход боя (очки / время / ничья) → `winner_fencer_id` + `ended_by`;
- сбор payload матча: в записи есть оба id и оба имени;
- outbox: ошибка insert → повтор без дубля (id матча генерируем на клиенте до отправки).

UI — на телефоне/узкой ширине: селекты пальцем, keep-awake как сейчас, логин переживает reload.

## Риски

- Две вкладки с одним логином: roster общий, текущий бой у каждой свой — так и задумано до realtime.
- Первый логин: без секретов в CI прод не заговорит с БД.
- Не писать счёт в Supabase на каждый укол «на всякий случай»: это ломает офлайн и табло.
- Не хранить в истории только `winner: 'blue'`. Цвет без человека непригоден для статистики; имя без id ломается на тёзках и переименованиях. Нужны оба.
