# Инвентаризация перед удалением `profiles`

SELECT-only. Это не миграция: не класть в `migrations/` и не гонять как изменение схемы.

Живая схема — после `#58` (person-строка, выход из клуба без смены id, слияние никнейма). Цель этапа 5: имя и `public_id` только в `fencers`, таблица `profiles` удаляется.

В **SQL Editor** роль `postgres` (как по умолчанию). Она обходит RLS. Вставь **весь файл**, выдели всё (`Ctrl/Cmd+A`), затем Run. Файлы начинаются с SQL, не с комментария: иначе редактор шлёт пустой запрос и Postgres отвечает `syntax error at end of input` / `LINE 0`.

Сначала [`00_counts.sql`](./00_counts.sql). Если какой-то `review` не ноль — [`01_rows.sql`](./01_rows.sql).

| `kind` | Смысл |
| --- | --- |
| `info` | Объём или уже целевое состояние. Дроп не блокирует. |
| `review` | Починить или решить до `DROP TABLE profiles`. Для дропа все такие строки должны быть 0. |

`review`, которые должны быть 0:

- **A** — профиль без person-строки в `fencers`. После дропа имя и номер пропадут, пока не сделать person-строку.
- **C** — person без `public_id`. Lookup по ID после дропа не найдёт человека.
- **D** — `profiles.public_id` ≠ `fencers.public_id` у одного `user_id`. Неясно, какой номер оставить.
- **F** — один `user_id` на нескольких `fencers` (уникальный индекс не должен этого допускать).
- **I** — один `public_id` на двух person-строках.

Не блокер:

- **B** — person без `profiles`. Уже целевая модель, если есть имя и `public_id`.
- **E** — имя в `fencers` и `profiles` разное. После дропа остаётся имя с `fencers`.
- **A2** — `auth.users` без профиля и без person: онбординг не закончен, имени ещё нет.
